# Releasing

How jnativekit is published to Maven Central. The build side is automated; the first
publication and every release are run by the owner, because they need credentials and a
manual review step.

`core` and `providers` are published as `io.github.atharvashelkeatwork:jnativekit-core` and
`...:jnativekit-providers`. The parent POM is published too. `demo` is never published
(`skipPublishing`).

## What is already wired

- `mvn -B verify` builds sources and Javadoc jars for every module.
- The `central` profile (`mvn -B -Pcentral ...`) adds GPG signing at `verify` and the
  Central Portal publishing plugin at `deploy`.
- `.github/workflows/release.yml` runs on a `v*` tag: it checks that the tag matches
  `project.version`, imports the signing key, runs every test tier, then deploys.
- `autoPublish` is `false`. The workflow stops after Central has *validated* the bundle;
  a human publishes the deployment in the Portal.

## Hard preconditions

Do not publish until all of these are true.

1. **v0.1.0 is verified.** The owner completed the manual checklist on Linux Mint 22.3
   (Cinnamon, X11) on 2026-11-04, and the rows are in `docs/TESTING.md`. The README support
   matrix maps to them. The owner has no Windows or macOS machine, so no release text may claim
   manual verification outside Linux. Windows and macOS are covered by CI (`ci-integration`) and
   the unit/unit-fake tiers only.
2. **The repository name matches the POM.** `pom.xml`, `README.md` and `CHANGELOG.md` use
   `https://github.com/atharvashelkeatwork/jnativekit`. The repository was renamed from `JNK`
   to `jnativekit` on 2026-11-04, so these URLs resolve. Maven Central records the SCM URL
   permanently.
3. **The namespace is verified.** In the [Central Portal](https://central.sonatype.com),
   register and verify `io.github.atharvashelkeatwork` through GitHub. The groupId must
   match a verified namespace exactly.
4. **The signing key exists and its public half is published.** See below.
5. **The secrets exist on the repository.** See below.

## One-time owner setup

### 1. GPG key

Use a dedicated key with a passphrase. RSA 4096 is the least surprising choice for older
Portal validation.

```bash
gpg --quick-generate-key "Atharva Shelke <you@example.com>" rsa4096 sign never
gpg --list-secret-keys --keyid-format=long          # copy the fingerprint
gpg --armor --export <FINGERPRINT>                  # paste into the GPG_PRIVATE_KEY secret
gpg --keyserver keyserver.ubuntu.com --send-keys <FINGERPRINT>
```

Central needs the public key on a keyserver so consumers can verify the signatures. Upload
it before the first release.

### 2. Portal token

In the Central Portal: **Account → Generate User Token**. These are the credentials for
the `central` server id, not your login password.

### 3. Repository secrets

Add these under **Settings → Secrets and variables → Actions**:

| Secret | Value |
|---|---|
| `GPG_PRIVATE_KEY` | ASCII-armored private key from `gpg --armor --export-secret-keys <FINGERPRINT>` |
| `MAVEN_GPG_PASSPHRASE` | the key passphrase (empty only if the key has no passphrase) |
| `CENTRAL_USERNAME` | Portal user-token username |
| `CENTRAL_PASSWORD` | Portal user-token password |

The workflow uses the `release` environment. Add required reviewers there if you want a
second approval before a tagged commit can reach Central.

## Local dry run (no credentials, no upload)

This stages and bundles exactly what would be uploaded, signs nothing, and stops before the
upload. Run it before the first release. The plugin still looks up the `central` server id,
so point Maven at a throwaway settings file with placeholder values:

```bash
cat > /tmp/central-dry-run-settings.xml <<'EOF'
<settings>
  <servers>
    <server>
      <id>central</id>
      <username>dry-run</username>
      <password>dry-run</password>
    </server>
  </servers>
</settings>
EOF

mvn -B -Pcentral -s /tmp/central-dry-run-settings.xml \
  -Dgpg.skip=true -Dcentral.skipUpload=true deploy
```

The reactor writes one bundle to `target/central-publishing/central-bundle.zip`. Check that
it contains, for `core` and `providers`:

```
jnativekit-<module>-0.1.0.pom
jnativekit-<module>-0.1.0.jar
jnativekit-<module>-0.1.0-sources.jar
jnativekit-<module>-0.1.0-javadoc.jar
```

plus checksums (generated by the plugin) and no `jnativekit-demo` files. The parent
contributes only `jnativekit-parent-0.1.0.pom`. A real release adds the matching `.asc`
signature for every file; the dry run has none because signing is skipped.

## Cutting a release

1. Update the version in every `pom.xml` and add the `CHANGELOG.md` section. Commit.
2. Confirm the tag will match: the workflow expects `v<project.version>`.
3. Create and push an annotated tag:

   ```bash
   git tag -a v0.1.0 -m "jnativekit v0.1.0"
   git push origin v0.1.0
   ```

4. Watch the `Release` workflow. It re-runs `mvn -B verify -Pintegration` on Linux, then
   deploys. A failure leaves nothing published.
5. Open **Publishing → Deployments** in the Central Portal, review the validated bundle,
   and click **Publish**.
6. After Central syncs (usually minutes, sometimes longer), check the coordinates:

   ```
   https://repo1.maven.org/maven2/io/github/atharvashelkeatwork/jnativekit-core/0.1.0/
   ```

7. Create the GitHub release and attach the demo jar if you have not done so already.

## Rules and recovery

- **A published version is immutable.** You cannot replace `0.1.0` after it is released;
  publish `0.1.1` instead.
- **Never reuse a tag.** Delete a bad local tag only before it is pushed; once CI has seen
  it, move forward with a new version.
- **A failed validation is fixable.** If the Portal rejects the bundle, nothing is public.
  Fix the build, then re-run the workflow on a new patch version (or re-run the job on the
  same tag before anything was published).
- **Signing failures are usually environmental.** Check that `GNUPGHOME` points at the
  imported key, that the passphrase secret is correct, and that the key has not expired.
- Never commit a private key, a passphrase or a Portal token. They belong only in the
  repository secrets.
